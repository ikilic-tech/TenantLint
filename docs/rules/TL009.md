# TL009: RLS session variable uses session scope

## What it detects

PostgreSQL row-level security (RLS) session variables set with session scope instead of transaction-local scope:

- `SET app.tenant_id = ...` without `LOCAL` keyword
- `set_config('app.tenant_id', ..., false)` with third argument `false`

## Why it matters

Session-scoped variables persist across pooled connections. When a database connection is returned to the pool and reused by another request, the previous tenant's variable value is still active. This causes RLS policies to use the wrong tenant, leaking data.

## Examples

### Bad

```csharp
db.Database.ExecuteSqlRaw("SET app.tenant_id = @t", tenantId);
db.Database.ExecuteSqlRaw("SELECT set_config('app.tenant_id', @t, false)", tenantId);
```

### Good

```csharp
db.Database.ExecuteSqlRaw("SET LOCAL app.tenant_id = @t", tenantId);
db.Database.ExecuteSqlRaw("SELECT set_config('app.tenant_id', @t, true)", tenantId);
```

## How to suppress

Mark the method with `[CrossTenant("reason")]`.

## False-positive notes

`SET TRANSACTION ISOLATION LEVEL` and other non-variable SET statements are not flagged. Non-constant SQL strings are not analyzed.
