# TL003: Dapper raw SQL references tenant table without tenant filtering

| Property   | Value              |
|------------|--------------------
| ID         | TL003              |
| Category   | TenantIsolation    |
| Severity   | Warning (see also TL103: Info when tenant column appears in predicate) |
| Enabled    | Yes                |
| Code Fix   | No                 |

## What it detects

TL003 fires when a Dapper `SqlMapper` extension method (`Query*`, `QueryFirst*`, `QuerySingle*`, `QueryMultiple*`, `Execute*`, `ExecuteScalar*`, `ExecuteReader*`, and their `Async` variants) contains a constant or interpolated SQL string that references a known tenant table name. This includes SQL passed directly as a `string sql` parameter, or indirectly via `new CommandDefinition("...")`.

Detection is by symbol (`Dapper.SqlMapper`), not by method name alone. User-defined methods named `Query` or `Execute` on other types are not flagged.

## Why it leaks

Dapper queries bypass EF Core's global query filters entirely — they execute raw SQL against the database connection. When a Dapper call references a tenant-scoped table without filtering by the tenant column, it can read or modify data across all tenants.

```csharp
// This deletes rows from ALL tenants, not just the current one:
conn.Execute("DELETE FROM Customers WHERE IsDeleted = 1");
```

## Severity logic

- **TL003** (Warning, default): The SQL references a tenant table but no tenant column appears in a `WHERE`, `ON`, `AND`, or `OR` clause with a parameter placeholder.
- **TL103** (Info): A tenant column name (e.g., `tenant_id`, `TenantId`) appears in a predicate clause (`WHERE`, `ON`, `AND`, `OR`) adjacent to a parameter placeholder (`@param`, `{0}`, `$1`, `:param`). The filter is likely present but should be verified.

Tenant column in a `SELECT` list, `ORDER BY`, or `GROUP BY` does **not** downgrade to Info.

## Examples

### Bad (Warning)

```csharp
// TL003: 'Execute' references tenant table 'Customers' in raw SQL
// without apparent tenant filtering.
conn.Execute("DELETE FROM Customers WHERE IsDeleted = 1");
```

```csharp
// Tenant column in SELECT does not count as filtering:
conn.Execute("SELECT tenant_id, Name FROM Customers");
```

```csharp
// CommandDefinition with tenant table:
var cmd = new CommandDefinition("DELETE FROM Customers WHERE IsDeleted = 1");
conn.Execute(cmd);
```

### Informational (Info)

```csharp
// Tenant column in WHERE with parameter — downgraded to Info:
conn.Execute("DELETE FROM Customers WHERE tenant_id = @tid", new { tid = tenantId });
```

### Good (no diagnostic)

```csharp
// Non-tenant table — no diagnostic:
conn.Execute("DELETE FROM Countries WHERE Id = 1");
```

```csharp
// Non-constant SQL — no diagnostic (cannot analyze):
conn.Execute(GetDynamicSql());
```

```csharp
// Marked as intentional cross-tenant access:
[CrossTenant("Admin cleanup applies to all tenants")]
public void CleanupDeletedRecords(IDbConnection conn)
{
    conn.Execute("DELETE FROM Customers WHERE IsDeleted = 1");
}
```

## Scope exclusions

TL003 detects `Dapper.SqlMapper` extension methods only. The following are **not** covered:

- **Dapper.Contrib** (`Insert`, `Update`, `Delete`, `Get`, `GetAll`): These generate SQL dynamically at runtime. TL003 cannot analyze runtime-generated SQL.
- **Dapper.SqlBuilder** / **SqlKata**: Query builders that compose SQL at runtime are not analyzed.
- **Stored procedure calls**: When `commandType: CommandType.StoredProcedure` is used, the SQL parameter is a procedure name, not a query. TL003 does not distinguish command types — if the procedure name happens to match a table name, a false positive may occur. Suppress with `[CrossTenant("reason")]` or `.editorconfig`.
- **Non-`SqlMapper` methods**: User-defined extension methods on `IDbConnection` with names like `Query` or `Execute` are not flagged — TL003 verifies the containing type is `Dapper.SqlMapper`.
- **`CommandDefinition` from variables**: When a `CommandDefinition` is constructed elsewhere (e.g., returned from a factory method or passed as a parameter), TL003 cannot extract the SQL. Only inline `new CommandDefinition("...")` or local variable declarations (`var cmd = new CommandDefinition("...");`) are analyzed.

## How to suppress

```ini
[*.cs]
dotnet_diagnostic.TL003.severity = none
```

Or mark the method with `[CrossTenant("reason")]`:

```csharp
[CrossTenant("Billing reconciliation requires cross-tenant data")]
public void Reconcile(IDbConnection conn) { ... }
```

## False-positive notes

- **Non-constant SQL** is not analyzed. If the SQL is built at runtime (e.g., `GetSql()`, string concatenation with non-constant values), TL003 does not report.
- **Non-tenant tables** are not flagged. Only tables associated with tenant-scoped entities (discovered via EF Core `HasQueryFilter` or convention) are checked.
- **Global entities** (configured via `tenantlint.global_entities`) are excluded.
- **Word boundaries** are checked. A table named `Customers` will not match SQL containing `CustomerLogs`.
- **Heuristic limitation**: The predicate detection uses simple keyword scanning, not full SQL parsing. Complex subqueries or CTEs may not be correctly classified.
- **Stored procedures**: If a stored procedure name matches a tenant table name, TL003 may report a false positive. Suppress with `[CrossTenant]` or `.editorconfig`.
