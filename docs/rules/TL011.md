# TL011: Pooled DbContext has tenant filter on readonly constructor field

| Property   | Value              |
|------------|---------------------|
| ID         | TL011               |
| Category   | TenantIsolation     |
| Severity   | Warning             |
| Enabled    | Yes                 |
| Code Fix   | No                  |

## What it detects

TL011 fires at the `AddDbContextPool` or `AddPooledDbContextFactory` registration site when the registered DbContext type has a tenant query filter whose value is rooted in a `readonly` field set only in the constructor.

A related diagnostic, **TL111** (Info), fires on the DbContext type itself — regardless of how it is registered — as a heads-up that the pattern is unsafe if pooling is ever introduced.

## Why it leaks

When a DbContext is pooled, the constructor runs **once per pool slot**. On subsequent uses, the runtime retrieves the instance from the pool **without re-invoking the constructor**. A `readonly` field set in the constructor retains the first tenant's value for every subsequent request that reuses that pool slot.

EF Core parameterizes query filter expressions through `this`, so the filter re-evaluates the field on each query. But if the field's value is stale (frozen at construction time), the "re-evaluated" value is still the wrong tenant's.

```csharp
// This LEAKS when pooled: _tenantId keeps the first tenant's value
public class AppDbContext : DbContext
{
    private readonly string _tenantId;

    public AppDbContext(DbContextOptions<AppDbContext> options, string tenantId) : base(options)
    {
        _tenantId = tenantId; // Only runs once per pool slot!
    }

    protected override void OnModelCreating(ModelBuilder m)
    {
        m.Entity<Order>().HasQueryFilter(e => e.TenantId == _tenantId);
    }
}

// Registration site — TL011 fires here:
services.AddDbContextPool<AppDbContext>((sp, o) => { ... });
```

## Examples

### Bad

```csharp
// TL011 at registration, TL111 on the DbContext
public class AppDbContext : DbContext
{
    private readonly string _tenantId; // TL111: readonly, set in ctor

    public AppDbContext(DbContextOptions<AppDbContext> o, string tenantId) : base(o)
    {
        _tenantId = tenantId;
    }

    protected override void OnModelCreating(ModelBuilder m)
    {
        m.Entity<Order>().HasQueryFilter(e => e.TenantId == _tenantId);
    }
}

// TL011: pooled + readonly tenant field
services.AddDbContextPool<AppDbContext>((sp, o) => o.UseSqlite("..."));
```

```csharp
// Also unsafe: readonly service field injected via constructor
public class AppDbContext : DbContext
{
    private readonly ITenantService _tenantService; // TL111

    public AppDbContext(DbContextOptions<AppDbContext> o, ITenantService svc) : base(o)
    {
        _tenantService = svc;
    }

    protected override void OnModelCreating(ModelBuilder m)
    {
        m.Entity<Order>().HasQueryFilter(e => e.TenantId == _tenantService.TenantId);
    }
}
```

### Good

```csharp
// Mutable field — can be updated after pool retrieval
public class AppDbContext : DbContext
{
    private string _tenantId = null!;

    public void SetTenant(string tenantId) => _tenantId = tenantId;

    protected override void OnModelCreating(ModelBuilder m)
    {
        m.Entity<Order>().HasQueryFilter(e => e.TenantId == _tenantId);
    }
}

// Safe: set tenant after pool retrieval via IDbContextFactory pattern
services.AddPooledDbContextFactory<AppDbContext>(o => o.UseSqlite("..."));
```

```csharp
// Non-pooled registration — readonly is fine
services.AddDbContext<AppDbContext>((sp, o) => o.UseSqlite("..."));
```

## How to suppress

```ini
[*.cs]
dotnet_diagnostic.TL011.severity = none
dotnet_diagnostic.TL111.severity = none
```

## False-positive notes

- **Non-pooled registration** (`AddDbContext`) does not trigger TL011. Readonly fields are safe when the constructor runs per-request.
- **Readonly auto-properties** (e.g., `private string TenantId { get; }`) are not flagged in v0.2 — only explicit `readonly` fields. This is a known limitation.
- **`IEntityTypeConfiguration`** classes are not analyzed for TL111.
- **TL111** (Info) fires even when the DbContext is not pooled. It serves as a warning that pooling would be unsafe with the current design.
